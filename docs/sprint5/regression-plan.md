## 4. Критерії go / no-go

Перевіряються після прогону за даними журналу регресії, трекера і матриці (`regression-log.xlsx`, GitHub Issues, `traceability-matrix.xlsx`).

| № | Критерій | Поріг | Тип | Обґрунтування |
|---|---|---|---|---|
| **K1** | Немає відкритих дефектів Blocker і Critical | 0 (статуси New / Open / Reopened) | безумовний | Дефект такої серйозності блокує основну функцію магазину — випуск неможливий за будь-яких інших чисел. |
| **K2** | Покриття вимог тестами | **High — 100 %**; загальне — **≥ 80 %** | безумовний | Вимог у SRS 1.1 — 41, з них High — 24. До регресії покрито 34 / 41 = 82,9 %. Непокриті — лише нефункціональні й документаційні вимоги, які потребують окремих інструментів або не перевіряються тестами інтерфейсу: GUI-80, GUI-100, P-10, P-20, U-10, D-10, D-20. Кожна функціональна вимога (F), GUI-функції й BL мають ≥ 1 кейс; F-130, S-10, S-20, U-20 і частина BL покриті частково — непокриту частину зазначено в `test-cases.xlsx` (аркуш Coverage) і в ризиках розділу 9 звіту. Поріг 80 % допускає непокриття лише таких вимог; кожна — з причиною в матриці. **Єдина непокрита High — P-10** (перша сторінка каталогу ≤ 3 с): її можна перевірити вручну через DevTools → Network, тому **до прогону додаємо кейс TC-032 (P-10)** — інакше K2 не виконано за визначенням. З TC-032: покриття 35 / 41 = 85,4 %, High 24 / 24 = 100 %. |
| **K3** | Частка пройдених кейсів (pass rate) | **≥ 80 %** (PR = passed / (passed + failed) · 100 %) | умовний | Відома база v1 (С3 Run 1 + С4): ручні 19 / 31 passed, JUnit 30 / 41 методів passed (11 методів червоні через BUG-015…020), UI 8 / 8 → **57 / 80 = 71,3 %**. Дефекти demo (BUG-001…014, усі P3) контролює постачальник, а не розробники модуля — вони не заявлені як виправлені, тому ~12 ручних кейсів очікувано лишаться Failed. Якщо v2 справді виправляє дефекти модуля (+11 методів), PR = 68 / 80 = 85 % (TC-032 — новий кейс без бази v1, у розрахунок бази не входить). Поріг 80 % означає: «виправлення модуля здебільшого підтверджено, Failed лишаються лише через відомі дефекти demo». |
| **K4** | Немає відкритих регресійних дефектів v2 | 0 (тест passed на v1 → failed на v2, без статусу Closed) | безумовний | Продукт не може бути гіршим за попередню версію. |
| **K5** | Повнота прогону | Частка виконаних E = (passed + failed) / усіх · 100 % = **100 %**, або кожен Blocked перевиконано / обґрунтовано виключено | безумовний | Без повного прогону PR і висновок не мають сенсу. |

### Правило рішення

| Рішення | Умова |
|---|---|
| **go** | Виконано всі K1–K5 |
| **умовний go** | Порушено лише K3. Умова — конкретний перелік дефектів до виправлення і дата повторної перевірки |
| **no-go** | Порушено хоча б один безумовний критерій (K1, K2, K4, K5) |

Висновок у звіті записується реченням виду: «Рішення …, оскільки критерій K… виконано / не виконано: <число> при порозі <поріг>».

## 5. Порядок дій

1. **До прогону:** звіти Surefire v1 (`TEST-*.xml`, `*.txt` з `target/surefire-reports/` прогону на `bb0df4f`, 104 тести) копіюються в `docs/sprint5/surefire-v1/`. Це «до». *(Звіти є в Кочарова Д. з відтворення С4 — передає ІТ.)*
2. **До прогону:** цей план злито в `main` (PR #67, 22.11.2026); TC-032 (P-10) додано в `test-cases.xlsx` (автор — Белінська Є., рецензент — не автор; рядок P-10 в аркуші Coverage).
3. **Модуль v2:** `src/test/java/...` з репозиторію копіюється у v2 (або v2 підключається модулем) → `mvn -q -B test` → звіти в `docs/sprint5/surefire-v2/`. Сигнатури v2 не змінювались — тести мають компілюватись без змін.
4. **UI:** `mvn test -DexcludedGroups=none` на поточному Sauce Demo.
5. **Ручні кейси:** кожен виконавець перевиконує свої кейси на поточному demo; результати — у `regression-log.xlsx` з датою і виконавцем (не копіюються з С3).
6. **Порівняння Surefire v1/v2 — по кожному тесту**, не за підсумком: Failed → Passed (кандидат Verified), Failed → Failed (кандидат Reopened), **Passed → Failed (регресія — новий дефект)**.
7. **Дефекти:** BUG-015…020 → Verified/Closed або Reopened з фактичним результатом на v2; BUG-001…014 — повторна перевірка за кроками → Open з коментарем «підтверджено на v2, дата» або Closed (not reproducible) з причиною. Новий регресійний дефект — окремий звіт із «регресія v2» у заголовку, посиланням на тест і результатом на v1.
8. **Матриця і метрики** (ТА) → перевірка K1–K5 (КТ) → розділ 9 звіту.
