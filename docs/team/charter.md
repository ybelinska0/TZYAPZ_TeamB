- **Тест-аналітик — Кочаров Давид:** аналіз очікувань замовника, формулювання user stories, їхніх ідентифікаторів і пріоритетів, простежуваність до очікувань, участь у таблицях елементів моделей.

- **Аудитор-опонент — Бобров Павло:** перевірка інкременту очима замовника до демо: відповідність моделей легенді, покриття беклогом усіх очікувань і ролей, перевірка DoD; підготовка акта аудиту `docs/sprint1/audit.md`, 5–7 очікуваних питань замовника та репетиція відповідей.

## 3. Правила комунікації

- **Основний канал зв'язку:** Telegram-чат команди.
- **Мова комунікації та документації:** професійна українська.
- **Асинхронний standup:** щосереди кожен учасник пише в Telegram два рядки: «Що зроблено з моїх задач» і «Що блокує роботу». Скрам-майстер збирає блокери та організовує їх обговорення.
- **Ретроспектива:** наприкінці кожного спринта команда використовує Start/Stop/Continue; Скрам-майстер фіксує домовленості в протоколі ретро.

## 4. Правила роботи з репозиторієм

- **Основна гілка:** `main` містить стабільну, перевірену версію документації та схем.
- **Робочі гілки:** створюються від `main` для задач, наприклад `feature/bpmn-models`.
- **Злиття:** через Pull Request після перевірки щонайменше одним іншим учасником команди. Автор не рецензує власний артефакт.
- **Коміти:** кожен працює під власним GitHub-логіном; повідомлення чітко описує зміну, наприклад `Додано статут команди charter.md`.

## 5. Правила оформлення та розміщення артефактів

1. Текстові документи оформлюються в Markdown; для кожної BPMN-моделі зберігаються вихідний файл `.drawio` або `.bpmn` та експорт у PDF або PNG.
2. Файли розміщуються за структурою інкременту: статут — `docs/team/charter.md`, артефакти спринта 1 — `docs/sprint1/`.
3. Назви файлів — латиницею без пробілів; у кожному документі зазначаються продукт, спринт, дата й автори.
4. Перевірені файли завантажуються до репозиторію GitHub без конфліктів злиття; посилання ведуть до наявних файлів і доступних документів.

Готовність усього інкременту визначається Definition of Done з §7 методички «Спринт 1 “Продукт і вимоги”». Норматив для команди з 5 осіб за §6: 4 BPMN-моделі, щонайменше 15 user stories і щонайменше 3 типи шлюзів у наборі моделей. За §8 до інкременту також входить акт Аудитора-опонента `docs/sprint1/audit.md`.

## 6. Методологія, методи і прийоми

| Рівень | Що застосовує команда |
|---|---|
| **Методологія** | Полегшений Scrum: п'ять двотижневих спринтів, Sprint Planning на початку, робота над інкрементом з регулярною синхронізацією, Demo й Retro наприкінці, ротація ролей щоспринта |
| **Методи** | Опис вимог через user stories з пріоритетами та простежуваністю до очікувань E1–E6; моделювання поточних процесів у BPMN за таблицями елементів; перехресне рецензування моделей за десятьма пунктами §4.9 і перевірка stories за шаблоном §4.12; аудит інкременту з погляду замовника Аудитором-опонентом |
| **Прийоми** | Standup у Telegram щосереди у два рядки «зроблено / блокує»; ретроспектива Start/Stop/Continue; для задачі визначаються виконавець і рецензент; PR перевіряє щонайменше один колега; перед рецензією таблиця елементів звіряється з діаграмою |
