## Пропозиції СМ до обговорення

**Continue (що працює)**
- Очікувані значення в тестах — зі SRS, а не з коду: PR #31 і #32 знайшли 4 закладені дефекти (BUG-015…018), кожен з Issue і тестом.
- Один тест-клас — один PR із рецензентом, який не автор.
- Зв'язок «тест → ID дефекту → Issue» у коментарях і Linked (як у PR #32).

**Stop (що заважає)**
- Змінювати production-класи модуля: `PromoCodeValidator.java` у `main` видаляли й створювали знову (09–10.11), довелося відновлювати (коміт «Відновлення оригінального PromoCodeValidator.java»); v1 має лишатися еталонним для спринта 5. Зараз файл збігається з еталоном байт-у-байт.
- Відкривати PR з тестами, не запустивши `mvn test` і не звіривши назви методів: PR #33 викликав неіснуючий `isValid`.
- Заводити Issues без міток `module` і `sprint:4` (#27, #28).

**Start (що почати)**
- Перед написанням тестів узгоджувати ID вимог і API класу (матриця покриття: BL-50 і довжина 5..10 замість BL-70 і 6..10).
- Для кожного правила писати нормальний випадок, межі з обох боків і заборонений вхід (прогалини: `Cart` — qty 1 і 99; `DiscountCalculator` — від'ємні значення для `shippingFee`).
- Заповнювати колонку рецензента в матриці покриття одразу після review.
- Визначити, як ставимо Priority для дефектів модуля (визначення P2/P3 зі спринта 3 стосується блокування тест-кейсів).
